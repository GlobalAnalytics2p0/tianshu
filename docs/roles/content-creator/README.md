# 內容創作者上任手冊

## 職責

內容創作者負責讓天書小說像長期連載作品，而不是一次性生成片段。重點是正文品質、連貫性、作者人格、伏筆節奏、人物清晰度與讀者黏著度。

## 必讀順序

每次新增、修訂或檢查小說內容前，依序讀取：

1. `agent.md`
2. `src/resource/writing-rules.md`
3. `src/resource/manifest.json`
4. `src/resource/五本長篇共通管理規範.md`
5. `src/resource/Share/Rule-of-Style.md`
6. 該作品的 `素材/風格規則.md`
7. 該作品的 `素材/核心靈魂檔案.md`
8. 該作品的 `素材/作者思路.md`
9. 該作品的 `素材/人物架構.md`
10. 該作品的 `素材/每日寫作狀態.md`
11. 該作品的 `素材/伏筆事件台帳.md`
12. 該作品的 `素材/反思.md`
13. 該作品 `文章/` 內所有既有 `.txt` 章節

五本 active 作品已全部採用新結構：企劃檔位於 `src/resource/<作品>/素材/`，章節正文位於 `src/resource/<作品>/文章/`。若未來新增 active 作品，必須先整理成同一結構再進入排程。

若上述 title-specific Markdown 沒讀到、讀錯作品、路徑指向混亂，或看起來不是最新版本，不得直接續寫；先停下來修正來源，再開始生成。

## 目前主責範圍

日常更新只針對五本類別代表作：

- `星骸王座`：玄幻，作者顧夜燼。
- `灰塔觀測者`：奇幻，作者霧原。
- `雪刃照孤城`：武俠，作者謝聽寒。
- `凌晨三點的演算法`：都市，作者陳停雲。
- `大明墨工`：歷史，作者蕭墨臣。

其他三十五本保留在網站與 `manifest.json` 裡，但預設不進六小時排程更新、影音或素材流程，除非使用者明確要求。

## 正文規格

- 新章節目標是 6,000-6,500 個繁體中文非空白字。
- 已發布章節預設鎖定，不為了新規格回頭補長。若使用者明確要求「全量品質重修」或明確點名包含已發布章節，才可改動已發布正文；這類改動必須分批、可驗證、可回滾，並同步更新 manifest、狀態、伏筆與反思。
- 小說正文只寫沉浸式內容，不寫章節安排、讀者提示、創作說明、automation 說明或大綱語。
- 每章應有一個清楚事件、一個小回報或反轉，3-5 章內要累積一次中回報，且章尾最後三行必須有具體追讀鉤子。
- AI 草稿最常見問題是均速：段落長度、揭露重量、情緒溫度都太平均。正式交稿前必須刻意調整快慢、急停、假鬆一口氣、再壓回來的節奏波形。
- 每次寫完都要更新 `manifest.json`、`每日寫作狀態.md`、`伏筆事件台帳.md`、`反思.md`，並在有耐久變動時同步更新 `核心靈魂檔案.md`、`作者思路.md` 或 `人物架構.md`。

## 寫作註記

- 如果寫作過程中產生值得保留的感觸、靈感、節奏判斷或踩雷，不要只記在腦中。
- 單本作品的下一章提醒、情緒重量、小人物用途、局部節奏感，寫進 `每日寫作狀態.md`。
- 單本作品的伏筆狀態、誤導方向、不能太早揭露的答案、回收時機，寫進 `伏筆事件台帳.md`。
- 單本作品的作者人格、中心思想、長期關係引擎或世界壓力來源修正，寫進 `核心靈魂檔案.md` 或 `作者思路.md`。
- 單本作品的資深閱讀者批評、反覆出現的弱點、下一章必須修正的讀感問題，寫進 `反思.md`。
- 只有會影響後續創作的心得才進耐久檔案；一次性的當場想法不需要硬寫。

## 內容品質審核

發布或交給工程流程前，至少檢查：

- 是否讀過既有章節與狀態檔，沒有前後矛盾？
- 是否保留長篇 1,500 章以上的 runway，沒有過早揭露終局？
- 是否避免模板化段落、manifest premise 直貼、重複句型與灌水？
- 主角壓力、欲望、恐懼、當下選擇是否清楚？
- 五本 active title 的作者聲音是否明顯不同？
- 小高潮後是否有必要的冷卻、代價或再蓄壓？
- 是否跑過 `node scripts/audit-active-novel-quality.mjs` 或等價檢查，確認必備 MD 存在、章節路徑正確、字數一致、沒有禁用 meta、沒有重複段落、最後三行有具體追讀鉤子？
- 是否人工確認腳本無法判斷的語意項：身歷其境、上癮感、小回報是否真正兌現、3-5 章中回報是否存在、該作者 `風格規則.md` 是否真的套用到正文？
- 六小時 automation 的正式交稿前 gate 是 `node scripts/supervise-ai-flow.mjs --phase post-generation --write-ledger`。如果 decision 不是 `ready-to-publish`，表示仍有硬性問題，正文、manifest 或狀態檔必須先修到過關。
- Supervisor 的 warnings 要當成資深讀者的下一輪提醒處理。若它反覆指出 AI 均速、前段缺轉向、章尾鉤子弱或跨書句型重疊，下一輪寫作前要先把這些警示轉成具體修稿動作，必要時寫入該作品 `反思.md` 或共通規則。

## 與其他角色交接

- 給社群總監：提供短 hook、人物/場景關鍵畫面、可公開但不劇透的賣點。
- 給全端工程師：提供章節檔路徑、字數、manifest 需要更新的 metadata、是否已發布鎖定。
- 內容交稿完成不等於網站已更新。若是 six-hour automation，預設必須在可連上 `origin` 的前提下完成 push，並等全端工程流程確認 `node scripts/verify-site-publication.mjs` 通過，才可對外回報「已上站」。若遠端不可達，除非使用者明確批准 local-only 例外，否則不應照常產出新章。
- 不直接處理大型音檔、影片輸出或社群後台發布。
